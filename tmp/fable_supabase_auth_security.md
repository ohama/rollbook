# Fable + Supabase 기반 운동 기록 웹앱

## 인증 / 보안 요구사항 정리

이 문서는 다음 요구를 만족하기 위한 설계를 정리한다.

-   이메일 + 비밀번호 회원가입
-   이메일 인증
-   비밀번호 초기화 / 재설정 (이메일)
-   로그인 상태 유지
-   본인 데이터 보호
-   사진 업로드 시 자동으로 운동 기록 생성
-   전체 통계 조회(정책적으로 허용된 범위)

프론트엔드는 **Fable(Elmish/Feliz)** 로 구현하며,
인증/DB/스토리지/권한은 Supabase 기능을 활용한다.

------------------------------------------------------------------------

## 전체 아키텍처

브라우저(Fable SPA) → Supabase Auth (로그인/이메일 인증/세션) → Supabase
DB(Postgres, RLS) → Supabase Storage → Edge Function (서버 로직)

핵심 원칙:

👉 **보안 규칙은 반드시 서버(Supabase)에서 강제**\
👉 프론트는 신뢰하지 않는다

------------------------------------------------------------------------

## 인증(Auth)

Supabase Auth가 다음을 기본 제공한다.

-   이메일/비밀번호 가입
-   인증 이메일 발송
-   비밀번호 재설정 메일
-   세션 관리

운영 환경에서는 커스텀 SMTP 설정을 권장한다.

------------------------------------------------------------------------

## 로그인 유지

Supabase 세션 메커니즘 사용.

프론트는: - 로그인 후 access token 획득 - API 호출 시 Authorization
헤더에 포함

------------------------------------------------------------------------

## DB 설계 (예시)

### workout_entries

-   id
-   user_id (auth.uid)
-   date (YYYY-MM-DD)
-   type?
-   minutes?
-   note?

권장 제약: UNIQUE(user_id, date)

→ 하루 1회 기록 모델을 단순하게 유지.

### workout_photos

-   id
-   user_id
-   entry_id
-   date
-   path
-   taken_at?

------------------------------------------------------------------------

## RLS (Row Level Security)

### 목표

-   사용자는 자신의 기록만 읽고/쓰고/수정 가능
-   전체 조회는 별도 정책(또는 Edge Function)

### 기본 패턴

    user_id = auth.uid()

미로그인 사용자는 auth.uid()가 null → 자동 차단.

------------------------------------------------------------------------

## Storage 보안

권장:

파일 경로를 아래 형태로 강제

    {user_id}/{YYYY-MM-DD}/filename

정책으로: - 본인 폴더만 업로드/조회 허용

public bucket 사용은 지양.

------------------------------------------------------------------------

## 사진 업로드 = 자동 운동 기록

이 로직은 **프론트에서 처리하지 않는다.**

반드시 Edge Function에서:

1.  토큰 검증
2.  날짜 결정 (기본 오늘)
3.  workout_entries upsert
4.  photo row 생성
5.  연결 완료

이렇게 해야 중복/조작을 방지할 수 있다.

------------------------------------------------------------------------

## 왜 이 구조가 안전한가

-   사용자가 API를 직접 호출해도
-   RLS 정책이 있기 때문에
-   자기 데이터 외 접근 불가

즉,

👉 프론트 해킹 ≠ 데이터 유출

------------------------------------------------------------------------

## Fable에서 구현 시 권장 패턴

프론트는:

-   DTO 타입 정의
-   API 호출 래퍼
-   상태 관리

까지만 담당.

권한, 검증, 자동 기록 같은 핵심 규칙은 모두 Supabase 측에 둔다.

## 결론

Fable + Supabase 조합은:

-   소규모 팀 운영에 충분히 강력하고
-   보안적으로도 표준적이며
