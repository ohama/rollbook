<task type="auto">
  <name>Task 2: Link local project to Supabase Cloud project</name>
  <files>supabase/.temp/project-ref (created by CLI)</files>
  <action>
After user creates Cloud project (via user_setup checkpoint), run `supabase link --project-ref <project-ref>`.

The project-ref is found in:
- Supabase Dashboard → Project Settings → General → Reference ID

This command:
1. Validates connection to Cloud project
2. Fetches remote configuration (PostgREST settings, auth config)
3. Creates local .temp/project-ref file to remember link
4. Checks if any migrations were already applied (should be none for new project)

IMPORTANT: Do NOT prompt user for database password - CLI uses API authentication, not direct database access.

If project already has migrations applied, STOP and warn user: "Project has existing schema. Fresh project required for clean migration."
  </action>
  <verify>
Run `supabase db remote` and confirm it shows database info for linked Cloud project.
Check output contains project-ref and database host (e.g., db.xxx.supabase.co).
  </verify>
  <done>
Local Supabase project linked to Cloud project. CLI can now push migrations and manage Cloud resources.
  </done>
</task>

<task type="auto">
  <name>Task 3: Push all local migrations to Supabase Cloud</name>
  <files>
    supabase/migrations/20260210014517_initial_schema.sql
    supabase/migrations/20260210100000_workouts_schema.sql
    supabase/migrations/20260210140000_team_visibility_rls.sql
    supabase/migrations/20260210150000_storage_bucket.sql
    supabase/migrations/20260210160000_admin_rbac.sql
  </files>
  <action>
Run `supabase db push` to apply all 5 migrations to Cloud database.

This command:
1. Reads all files in supabase/migrations/ in timestamp order
2. Checks supabase_migrations.schema_migrations table to see what's already applied
3. Applies pending migrations in transaction
4. Updates schema_migrations table with applied migrations

Expected output:
```
Applying migration 20260210014517_initial_schema.sql...
Applying migration 20260210100000_workouts_schema.sql...
Applying migration 20260210140000_team_visibility_rls.sql...
Applying migration 20260210150000_storage_bucket.sql...
Applying migration 20260210160000_admin_rbac.sql...
Finished supabase db push.
```

If any migration fails:
1. Check error message for SQL syntax issues
2. Migrations are atomic - failed migration rolls back
3. Fix issue in migration file and re-run `supabase db push`
4. DO NOT manually fix in Cloud SQL editor (breaks idempotency)

RESEARCH INSIGHT: Migrations are idempotent if using DROP POLICY IF EXISTS patterns (which our migrations already use). Safe to re-run.
  </action>
  <verify>
1. Run `supabase migration list` and confirm all 5 migrations show "Applied" status
2. Open Supabase Dashboard → SQL Editor and run:
   ```sql
   -- Check tables exist
   SELECT table_name FROM information_schema.tables
   WHERE table_schema = 'public'
   ORDER BY table_name;
   -- Expect: profiles, user_roles, workouts

   -- Check RLS enabled
   SELECT tablename, rowsecurity
   FROM pg_tables
   WHERE schemaname = 'public';
   -- Expect: all tables have rowsecurity = true

   -- Check storage bucket
   SELECT name, public FROM storage.buckets;
   -- Expect: workout-photos, public = false
   ```
3. All queries return expected results
  </verify>
