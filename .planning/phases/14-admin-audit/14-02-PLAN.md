Create PostgreSQL migration implementing admin role management RLS policies and default admin initialization.

**1. Add RLS policies for user_roles table (ADM-03):**
- CREATE POLICY "Admins can insert admin roles" ON public.user_roles FOR INSERT TO authenticated WITH CHECK (public.is_admin() AND role IN ('admin', 'member'));
  - Allows admins to grant roles to others
  - Restricts role values to 'admin' or 'member'
- CREATE POLICY "Admins can delete roles" ON public.user_roles FOR DELETE TO authenticated USING (public.is_admin());
  - Allows admins to revoke roles from others

**2. Update workouts SELECT RLS policy for admin soft-delete viewing:**
- DROP existing "Users can view own workouts" policy
- CREATE POLICY "Users can view own workouts or admins view all" ON public.workouts FOR SELECT TO authenticated USING (user_id = (SELECT auth.uid()) OR public.is_admin());
  - Regular users: see only their own workouts
  - Admins: see ALL workouts including deleted_at IS NOT NULL (no filter on deleted_at)
  - This enables ADM-05 (admin can see deleted records for restoration)

**3. Add RLS policy for audit.record_version (admin read-only):**
- ALTER TABLE audit.record_version ENABLE ROW LEVEL SECURITY;
- CREATE POLICY "Admins can view audit log" ON audit.record_version FOR SELECT TO authenticated USING (public.is_admin());
  - Only admins can read audit logs
  - No INSERT/UPDATE/DELETE policies needed (triggers write, humans never write directly)

**4. Initialize default admins (ADM-02):**
- INSERT INTO public.user_roles (user_id, role) SELECT id, 'admin' FROM auth.users WHERE email IN ('ohama100@gmail.com', 'ohama100@naver.com') ON CONFLICT (user_id, role) DO NOTHING;
  - Idempotent: ON CONFLICT DO NOTHING allows safe re-runs
  - Only inserts if users already exist in auth.users (they should from v1.0)

**5. Add comments:**
- COMMENT ON POLICY "Admins can insert admin roles" ON public.user_roles IS 'Allows admins to grant admin/member roles to users.';
- COMMENT ON POLICY "Admins can view audit log" ON audit.record_version IS 'Audit log is read-only for admins. Triggers write, humans read.';

**Why is_admin() in policies:** Existing function from Phase 6, efficient (indexed lookup), reusable (research Pattern 4).
**Why admin sees all workouts:** Necessary for viewing deleted records to enable restore functionality (research Open Question 1).
**Why audit.record_version SELECT-only:** Triggers write audit logs, humans should never modify them (research Anti-Patterns).

Create F# module implementing audit log queries and soft-delete restoration per research code examples.

**Module structure:**
```fsharp
module Supabase.Audit

open Fable.Core
open Fable.Core.JsInterop
open Supabase.Client
open Supabase.Types

// Display type for audit entries (match DB schema, keep simple)
type AuditEntry = {
    id: int64
    ts: string  // ISO timestamp
    op: string  // "INSERT" | "UPDATE" | "DELETE"
    user_email: string option
    table_name: string
    record: obj  // Raw JSONB, access with dynamic operators
    old_record: obj option
}
```

**Functions to implement:**

1. **getRecentChanges (limit: int) : JS.Promise<Result<AuditEntry array, string>>** (ADM-07)
   - Query audit.record_version with select("id, ts, op, user_email, table_name, record, old_record")
   - Order by ts descending: ?order("ts", createObj ["ascending" ==> false])
   - Limit results: ?limit(limit)
   - Parse response.data as AuditEntry array
   - Return Result.Ok entries or Result.Error errorMsg

2. **restoreWorkout (workoutId: int64) : JS.Promise<Result<unit, string>>** (ADM-08)
   - Update workouts table: ?update(createObj ["deleted_at" ==> null])
   - Match by id: ?eq("id", workoutId)
   - Return Result.Ok () or Result.Error errorMsg
   - Note: This un-deletes the record (sets deleted_at back to NULL)

3. **getDeletedWorkouts () : JS.Promise<Result<WorkoutRecord array, string>>** (for restore UI)
   - Query workouts with ?select("*")
   - Filter deleted only: ?not("deleted_at", "is", null)
   - Order by deleted_at descending: ?order("deleted_at", createObj ["ascending" ==> false])
   - Parse response.data as WorkoutRecord array
   - Return Result.Ok workouts or Result.Error errorMsg
   - Note: Admin RLS policy allows viewing deleted records

**Pattern matching existing modules:**
- Use same promise {} block structure as Supabase.Admin, Supabase.Workouts
- Use dynamic operators: supabase?from()? pattern
- Use createObj for JS object creation: createObj ["key" ==> value]
- Use unbox<T> for response.data parsing
- Handle errors with match box error pattern
- Return Result<T, string> for all operations

**JSONB handling:**
- Do NOT try to deserialize JSONB to F# records (research Pitfall 4)
- Keep record/old_record as obj type
- UI will access fields dynamically with ? operator

**Why Result<T, string>:** Consistent error handling pattern across codebase (see Admin.fs, Workouts.fs).
**Why obj for JSONB:** JSONB has snake_case keys that won't match F# record fields (research Pitfall 4).
**Why not("deleted_at", "is", null):** Supabase pattern for filtering non-NULL values (existing pattern from Phase 8).
