  <action>
Create Supabase migration file for workouts table following Phase 1 patterns:

**Table structure:**
- `user_id UUID` - references auth.users(id) ON DELETE CASCADE
- `workout_date DATE` - stores YYYY-MM-DD (4 bytes, no timezone confusion)
- `created_at TIMESTAMPTZ` - default now()
- PRIMARY KEY (user_id, workout_date) - enforces one workout per user per date
- Index on workout_date for date-range queries

**RLS policies (4 separate, not FOR ALL):**
1. SELECT: "Users can view own workouts" - USING ((SELECT auth.uid()) = user_id)
2. INSERT: "Users can insert own workouts" - WITH CHECK ((SELECT auth.uid()) = user_id)
3. UPDATE: "Users can update own workouts" - USING/WITH CHECK both use auth.uid()
4. DELETE: "Users can delete own workouts" - USING ((SELECT auth.uid()) = user_id)

**Critical details from RESEARCH.md:**
- Use DATE type (not TIMESTAMPTZ) - matches "did I workout today" semantics, 4 bytes vs 8
- Wrap auth.uid() in (SELECT auth.uid()) - caches result per statement, ~95% performance improvement
- Enable RLS immediately after table creation (CVE-2025-48757 prevention)
- Add comment on table documenting RLS enabled

**Follow Phase 1 migration format:**
- Extension checks (uuid-ossp if needed)
- Table comment documenting purpose
- Performance-optimized RLS with SELECT wrapper

**Do NOT:**
- Use FOR ALL policy (harder to debug, less clear intent)
- Store TIMESTAMPTZ for workout_date (unnecessary complexity)
- Forget ON DELETE CASCADE (orphaned records on user deletion)
