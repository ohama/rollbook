# Phase 6: Production Ready - Research

**Researched:** 2026-02-10
**Domain:** Progressive Web Apps (PWA), Offline-First Architecture, Production Hardening
**Confidence:** HIGH

## Summary

Phase 6 focuses on making the Fable/Feliz application production-ready through PWA capabilities, offline functionality, admin tooling, and security hardening. The standard approach uses `vite-plugin-pwa` with Workbox for service worker generation, IndexedDB for offline data storage, and Supabase Row Level Security (RLS) for admin access control.

Key technical challenges include implementing offline-first patterns without complex sync libraries (Supabase doesn't natively support offline sync), managing service worker lifecycle in development, and achieving the <500KB bundle size target with F# compiled to JavaScript.

The production hardening checklist centers on Supabase Security Advisor compliance, proper RLS configuration, and performance optimization through bundle analysis and code splitting.

**Primary recommendation:** Use vite-plugin-pwa with generateSW strategy for zero-config PWA setup, implement simple IndexedDB queue for offline writes with Background Sync API, and leverage Supabase custom claims for admin RBAC.

### Pattern 3: Offline Queue with IndexedDB
**What:** Queue failed requests in IndexedDB, replay with Background Sync
**When to use:** Apps needing offline write capability without full sync
**Example:**
```typescript
// Source: https://blog.logrocket.com/offline-first-frontend-apps-2025-indexeddb-sqlite/
import { openDB } from 'idb';

const db = await openDB('rollbook-offline', 1, {
  upgrade(db) {
    db.createObjectStore('queue', { keyPath: 'id', autoIncrement: true });
  }
});

// Queue a workout submission
async function queueWorkout(workout) {
  await db.add('queue', {
    timestamp: Date.now(),
    action: 'POST',
    url: '/api/workouts',
    data: workout
  });

  // Register background sync
  const registration = await navigator.serviceWorker.ready;
  await registration.sync.register('sync-workouts');
}

// In service worker (sw.js)
self.addEventListener('sync', (event) => {
  if (event.tag === 'sync-workouts') {
    event.waitUntil(replayQueue());
  }
});

async function replayQueue() {
  const items = await db.getAll('queue');
  for (const item of items) {
    try {
      await fetch(item.url, {
        method: item.action,
        body: JSON.stringify(item.data)
      });
      await db.delete('queue', item.id);
    } catch (err) {
      console.error('Sync failed, will retry', err);
    }
  }
}
```

### Pattern 4: Admin Role-Based Access with Supabase
**What:** Use custom claims in JWT for admin role, enforce with RLS
**When to use:** Admin vs regular user access control
**Example:**
```sql
-- Source: https://supabase.com/docs/guides/database/postgres/custom-claims-and-role-based-access-control-rbac

-- 1. Create user_roles table
CREATE TABLE public.user_roles (
  user_id uuid REFERENCES auth.users NOT NULL,
  role text NOT NULL,
  PRIMARY KEY (user_id, role)
);

-- 2. Create authorize function
CREATE OR REPLACE FUNCTION public.authorize(
  requested_permission text
)
RETURNS boolean AS $$
DECLARE
  user_role text;
  has_permission boolean;
BEGIN
  -- Get user role from JWT custom claims
  SELECT (auth.jwt() -> 'user_metadata' ->> 'role') INTO user_role;

  -- Check if role has permission
  SELECT EXISTS (
    SELECT 1 FROM public.role_permissions
    WHERE role = user_role AND permission = requested_permission
  ) INTO has_permission;

  RETURN has_permission;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- 3. Apply RLS policy for admin delete
CREATE POLICY "Admin can delete members"
ON public.members
FOR DELETE
USING (authorize('members.delete'));

-- 4. Insert admin role
INSERT INTO public.user_roles (user_id, role)
VALUES ('admin-user-uuid', 'admin');

INSERT INTO public.role_permissions (role, permission)
VALUES ('admin', 'members.delete');
```

### Anti-Patterns to Avoid

- **Service worker caching auth tokens:** Never cache authenticated requests; use `NetworkFirst` or `NetworkOnly` for Supabase API calls
- **Storing sensitive data in localStorage:** Use IndexedDB for structured data, never store tokens in localStorage (vulnerable to XSS)
- **Hand-rolling sync logic:** Don't build custom conflict resolution without understanding CRDT/OT complexity
- **Caching POST/PUT/DELETE in service worker:** Only cache GET requests; mutations must reach server
- **Forgetting to unregister SW in dev:** Service workers persist across sessions; unregister in DevTools when debugging

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| IndexedDB API | Raw promise chains with `onSuccess` callbacks | `idb` library | 1KB wrapper eliminates callback hell, adds promise support |
| PWA manifest generation | Manual JSON + icon creation | `vite-plugin-pwa` + `@vite-pwa/assets-generator` | Auto-generates manifest, SW, and icons from config |
| Service worker caching | Custom fetch interception logic | Workbox strategies (via vite-plugin-pwa) | Battle-tested cache-first, network-first, stale-while-revalidate |
| Offline conflict resolution | Custom last-write-wins with timestamps | Accept simple queue or use PowerSync/RxDB | CRDTs are hard; even "simple" sync has edge cases (concurrent edits, partial updates) |
| Bundle analysis | Manual webpack stats parsing | `rollup-plugin-visualizer` | Interactive treemap, gzip/brotli sizes, treeshake visualization |
| Background sync detection | Custom online/offline listeners | Background Sync API | Handles network transitions, retries, even if tab closed |

**Key insight:** Offline-first is deceptively complex. For simple use cases (queue writes, sync when online), use Background Sync API + IndexedDB queue. For true bidirectional sync with conflict resolution, use a specialized library (PowerSync, RxDB, ElectricSQL) rather than building custom logic.

## Common Pitfalls

### Pitfall 1: Service Worker Not Updating in Development
**What goes wrong:** Changes to service worker don't reflect; browser serves cached version
**Why it happens:** Service workers persist across page reloads and even browser sessions
**How to avoid:**
- Use `vite-plugin-pwa` with `devOptions: { enabled: true }` for hot reload
- Manually unregister in DevTools (Application > Service Workers > Unregister)
- Change cache version in `service-worker.js` to force update
**Warning signs:** "I changed the code but nothing happened"; seeing old cached responses

### Pitfall 2: RLS Enabled Without Policies = Zero Access
**What goes wrong:** After enabling RLS, all queries return empty, even for authenticated users
**Why it happens:** RLS with no policies = deny all by default
**How to avoid:** Always create at least one policy when enabling RLS; use Security Advisor to check
**Warning signs:** `SELECT` queries return 0 rows despite data existing; Supabase client shows no errors

### Pitfall 3: `auth.uid() = user_id` Fails for Unauthenticated
**What goes wrong:** Policies silently fail when unauthenticated users access the app
**Why it happens:** `auth.uid()` returns `null` for anonymous users; `null = anything` is always false in SQL
**How to avoid:** Use `(SELECT auth.uid()) = user_id` and add explicit `IS NOT NULL` checks
**Warning signs:** Authenticated users see data, unauthenticated users see nothing (when you expect public read)

### Pitfall 4: IndexedDB Not Available in Service Worker Context (False)
**What goes wrong:** Developers think they can't use IndexedDB in service workers
**Why it happens:** Old documentation or confusion with localStorage (which IS unavailable in SW)
**How to avoid:** IndexedDB works in service workers; localStorage does NOT; use IndexedDB for offline queue
**Warning signs:** Using Cache Storage API for structured data instead of IndexedDB

### Pitfall 5: Background Sync Only Works in Chromium (2026)
**What goes wrong:** Background Sync not working in Firefox/Safari
**Why it happens:** Background Sync API support is limited to Chromium browsers (Chrome, Edge, Opera)
**How to avoid:** Feature detect `'sync' in registration` and fallback to manual retry on page load
**Warning signs:** Offline queue never replays in Firefox/Safari

### Pitfall 6: Bundle Size Bloat from Fable Runtime
**What goes wrong:** F# compiled code includes large runtime, exceeding 500KB limit
**Why it happens:** Fable compiles F# to JavaScript with some runtime overhead; importing entire libraries
**How to avoid:**
- Use `rollup-plugin-visualizer` to identify large dependencies
- Apply manual chunking to separate vendor code
- Ensure tree-shaking works (use ES2015 imports, not wildcards)
- Consider code splitting for admin routes
**Warning signs:** Initial bundle > 500KB even for simple app

### Pitfall 7: PWA Not Installable on iOS
**What goes wrong:** iOS Safari doesn't show "Add to Home Screen" prompt
**Why it happens:** iOS doesn't show automatic prompts; users must manually share > Add to Home Screen
**How to avoid:**
- Provide in-app instructions for iOS users
- Ensure manifest has required fields (`name`, `icons`, `start_url`, `display`)
- Test on iOS 16.4+ (earlier versions have limited PWA support)
**Warning signs:** Works on Android, not on iOS; no install prompt

### Workbox Caching Strategies
```javascript
// Source: https://developer.chrome.com/docs/workbox/caching-resources-during-runtime
// In vite.config.ts > VitePWA > workbox.runtimeCaching

// Cache-first for static assets (images, fonts)
{
  urlPattern: /\.(?:png|jpg|jpeg|svg|gif|webp|woff2)$/,
  handler: 'CacheFirst',
  options: {
    cacheName: 'static-assets',
    expiration: {
      maxEntries: 100,
      maxAgeSeconds: 30 * 24 * 60 * 60 // 30 days
    }
  }
}

// Network-first for API calls with timeout
{
  urlPattern: /^https:\/\/.*\.supabase\.co\/rest\/.*/,
  handler: 'NetworkFirst',
  options: {
    cacheName: 'supabase-api',
    networkTimeoutSeconds: 10, // Fallback to cache after 10s
    expiration: {
      maxEntries: 50,
      maxAgeSeconds: 5 * 60 // 5 minutes
    }
  }
}

// Stale-while-revalidate for profile images
{
  urlPattern: /^https:\/\/.*\.supabase\.co\/storage\/.*/,
  handler: 'StaleWhileRevalidate',
  options: {
    cacheName: 'profile-images'
  }
}
```

### Supabase RLS Performance Optimization
```sql
-- Source: https://supabase.com/docs/guides/database/postgres/row-level-security

-- SLOW: auth.uid() not cached
CREATE POLICY "Users view own workouts"
ON workouts FOR SELECT
USING (auth.uid() = user_id);

-- FAST: Wrapped in SELECT for query optimizer
CREATE POLICY "Users view own workouts"
ON workouts FOR SELECT
USING ((SELECT auth.uid()) = user_id);

-- CRITICAL: Add index on RLS-checked columns
CREATE INDEX idx_workouts_user_id ON workouts(user_id);

-- COMBINED: Policy + explicit filter for best performance
-- Client code:
SELECT * FROM workouts
WHERE user_id = auth.uid() -- Explicit filter
-- Policy still enforces security, but query optimizer can use index
```

### Background Sync with Feature Detection
```javascript
// Source: https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API

// Register sync with fallback
async function queueWorkoutWithSync(workout) {
  await queueInIndexedDB(workout);

  const registration = await navigator.serviceWorker.ready;

  if ('sync' in registration) {
    // Chromium browsers: use Background Sync
    await registration.sync.register('sync-workouts');
  } else {
    // Firefox/Safari: fallback to manual sync on visibility change
    document.addEventListener('visibilitychange', () => {
      if (document.visibilityState === 'visible') {
        replayQueue();
      }
    });
  }
}

// Service worker
self.addEventListener('sync', (event) => {
  if (event.tag === 'sync-workouts') {
    event.waitUntil(replayQueue());
  }
});
```

## Open Questions

Things that couldn't be fully resolved:

1. **Fable bundle size with Feliz + Supabase client**
   - What we know: Fable supports tree shaking, Vite minifies output, typical React apps can hit <500KB
   - What's unclear: Actual compiled size of current Rollbook codebase; Feliz + Supabase client overhead
   - Recommendation: Run `rollup-plugin-visualizer` on current build to establish baseline before optimization

2. **Background Sync API fallback strategy**
   - What we know: Background Sync only works in Chromium; Firefox/Safari need manual retry
   - What's unclear: Best UX pattern for non-Chromium browsers (toast notification? auto-retry on visibility change?)
   - Recommendation: Implement feature detection, fallback to visibility change listener, test on Safari iOS

3. **Conflict resolution for offline edits**
   - What we know: Simple queue works for create-only operations; edits/deletes need conflict handling
   - What's unclear: Does the app allow editing past workouts while offline? Or just create new?
   - Recommendation: If create-only, simple queue is sufficient; if edit/delete, add "last-write-wins" with server timestamp check

4. **Admin role assignment flow**
   - What we know: Custom claims in JWT, RLS policies for authorization
   - What's unclear: How are users promoted to admin? Manual DB insert? Admin UI? Invitation system?
   - Recommendation: Start with manual DB insert for MVP, add admin UI in future phase if needed
